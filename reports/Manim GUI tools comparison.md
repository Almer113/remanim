# Manim GUIs multiply, but code still rules

As of November 2026 no Manim GUI has become a standard authoring tool. What people actually use are **viewers that sit beside code**, not canvases that replace it. The only mass-adoption GUI is **Manim Sideview**, a VS Code render-on-save panel with about 129.5k installs. Every true visual editor is either dead (kevcen/manimate, MathItYT's manim-studio, ManimCommunity's manim_editor) or a weeks-old 2026 project with 105 stars or fewer. The newest wave splits two ways. Some are classic canvas-plus-timeline editors that write Python one way (diegormirhan/manim-editor). The others are AI-agent studios that keep Python as the single source of truth and use the GUI only to review and retime it (lukaznj's Manim Studio, pachterlab's Manimble). The reason is architectural. A Manim scene is an imperative Python program with no persistent scene graph and with timing implied by the order of `play()` calls, so a GUI can either re-run the code and show video, or edit a narrow, well-defined slice of it. It cannot round-trip arbitrary Python. For this project (Manim CE 0.22.1 on Windows, Python 3.13, Claude Code, `preview_server.py`, check tools and `manim_kit.py`) the conclusion is plain. **None of the GUIs is worth adopting as a replacement**: most pin older Manim versions, bundle their own Python (which cannot see `style.py` or `manim_kit.py`), target macOS or ManimGL, or duplicate what Claude Code already does. The two items worth acting on are manim-slides (if presentations are needed) and Manim Cue, a core developer's VS Code extension. Cue is worth watching once the next CE release lands, and its timeline-to-source-line design is worth copying into the existing preview server.

## Fewer than ten real visual editors exist, and none has passed the toy stage

A search across about 30 GitHub queries found a thin niche. Queries for "manim pyqt", "manim electron", "manim node editor" and "manimgl gui" returned nothing. **The best-starred true WYSIWYG editor, kevcen/manimate (140 stars), has had no commit since July 2024** and pins `manim==0.15.2`, PySide6 6.3 and Python 3.10 ([requirements.txt](https://github.com/kevcen/manimate/blob/main/requirements.txt)). Its design was sound: an object palette, a property panel and "states" that the tool interpolates into Manim code ([README](https://github.com/kevcen/manimate)). MathItYT's PyQt6 **manim-studio** offered live Cairo preview and could attach to an existing scene, but its last release, 0.7.4 (March 2024), requires `manim>=0.18,<0.19` and Python `<3.13`. **It cannot even install into this project's Python 3.13 venv** ([PyPI](https://pypi.org/pypi/manim-studio/json)). The standalone client was also pulled after antivirus programs flagged it ([PyPI 0.6.8](https://pypi.org/project/manim-studio/0.6.8)). ManimCommunity's own **manim_editor** (364 stars) is a section-based web presenter, not an animation editor, and pins `manim<0.14` ([PyPI](https://pypi.org/pypi/manim-editor/json)).

The 2026 projects are newer and more polished but just as unproven. **diegormirhan/manim-editor** is a Windows-only Tauri app with a layered timeline, drag/scale/rotate on stage, and a live preview that shows "Manim's own frame at the playhead, usually within half a second" from a resident Manim process. It exports MP4/WebM/GIF/MOV, readable Python, and even per-layer ProRes 4444 with FCPXML timelines for Premiere and Resolve. It pins `manim==0.21.0` in a bundled runtime, has no licence file, has 3 stars, and calls itself "a development MVP". It also cannot read code back: "Existing Manim Python cannot be imported, and exported Python is not read back" ([README](https://github.com/diegormirhan/manim-editor); [requirements.txt](https://github.com/diegormirhan/manim-editor/blob/main/requirements.txt)). **pachterlab/Manimble** (105 stars, BSD-2-Clause, v0.4.7 on 16 November 2026) is the most credible, coming from Lior Pachter's lab. Each slide is Python, editable "on the canvas like in PowerPoint or Keynote, in the built-in code editor, or with an AI coding agent such as Claude Code", and all three can work on the same deck at once. **It is macOS-only; Windows is "planned"** ([README](https://github.com/pachterlab/Manimble)). **lukaznj/manim-studio** (AGPL-3.0, 1 star, near-daily releases) ships a Windows installer. Its timeline "comes from the render": every `self.play`, section, narration line and subtitle is linked to its line of code, and "drag a clip's edge and the `run_time=` in the code changes". An AI agent (Claude, Codex or Gemini) writes `scene.py` and fixes the layout. On first launch it downloads about 750 MB of Python and Manim plus 250 MB of LaTeX ([README](https://github.com/lukaznj/manim-studio)). **AniMathIO 2** (MIT, Rust, Windows/macOS/Linux, v2.2.0 in November 2026) has a real multi-track keyframe timeline, MCP control and local Whisper subtitles. However, it renders with its own Rust/Vello engine and Typst, and its Manim support is a **one-way importer** that converts CE scripts into its own format ([README](https://github.com/AniMathIO/AniMathIO); [architecture](https://github.com/AniMathIO/AniMathIO/blob/main/docs/architecture.md)).

Below these sits a long tail. LzdqesjG/ManimEditor (2 stars, `manim>=0.19`) uses reflection to build forms for about 148 Mobjects and 77 Animations and merges same-start clips into one `self.play()` ([README](https://github.com/LzdqesjG/ManimEditor)). EfficientManim is a node-graph IDE, idle since June 2026 ([README](https://github.com/programmersd21/EfficientManim)). EasyManim offers only circle, square and text ([README](https://github.com/tailwiinder/easymanim)). BlommeJan/Manim-Motion is a Figma-like browser editor that renders through Docker and has no LICENSE file ([README](https://github.com/BlommeJan/Manim-Motion)). Most of the rest are 0-star "vibecoded" prototypes or 2020–2024 abandonware. **No Blender- or Godot-style editor that exports Manim code exists**, and every visual editor found targets Manim CE, not ManimGL. Two caveats matter in practice. First, names collide badly: "Manim Studio" refers to at least five unrelated projects ([gh search](https://github.com/search?q=manim+studio&type=repositories&s=stars)). Second, two 0-star repos (lorileeconsumptive6527/manim-editor, dunhillwilliam/manimeditor) fit the pattern of malware lure repos, so their binaries should not be downloaded.

## The tools people actually use are viewers bolted onto the CLI

The editor-side tools tell a different story, because they never try to replace code. **Manim Sideview** (Rickaym, MIT, v0.4.3, updated 9 September 2026) has 129,495 Marketplace installs plus 13,118 on Open VSX for Cursor and VSCodium. It renders the current scene on save and plays the result in a side panel with seeking and looping ([Marketplace](https://marketplace.visualstudio.com/items?itemName=Rickaym.manim-sideview); [README](https://github.com/Rickaym/Manim-Sideview)). Its author is frank that "the underlying rendering command is the same command for rendering that we would usually do", which means it saves no rendering time ([Discussion #3954](https://github.com/ManimCommunity/manim/discussions/3954)). Smaller extensions fill the same niche: Manim Viewer (9.4k installs, re-renders only when code changed), MarkHoo's Runner and LiveView, and the Open VSX-only manim-dock ([Marketplace search](https://marketplace.visualstudio.com/search?term=manim&target=VSCode)).

The most interesting newcomer is **Manim Cue**, published by Benjamin Hackl, a Manim CE core developer (MIT, v0.3.1, 12 November 2026, 76 installs). After a save it shows the frame at a chosen time and then a **timeline of plays, waits, sections, captions and sounds**. Each timeline entry jumps to its source line. It also does wipe and overlay frame comparison, measures coordinates in scene units, and labels stale frames "OUTDATED" during re-renders. **It needs Manim CE from the unreleased `main` branch "until the next Manim release"**, plays silently, and does not say whether it supports Windows ([Marketplace](https://marketplace.visualstudio.com/items?itemName=behackl.manim-cue)). For ManimGL, **Manim Notebook** (2.5k installs, MIT) reproduces Grant Sanderson's `##`-cell workflow, but its last release was April 2025. An open report says that on Windows 11 its injected `checkpoint_paste()` is typed into the terminal but never runs ([Marketplace](https://marketplace.visualstudio.com/items?itemName=Manim-Notebook.manim-notebook); [issue #18 mirror](https://cf-workers-proxy-9e9.pages.dev/Manim-Notebook/manim-notebook/issues/18)). Every ManimGL extension wraps that same terminal-paste mechanism and inherits its fragility. Outside VS Code there is little: Grant's own Sublime commands for ManimGL ([3b1b/videos](https://github.com/3b1b/videos)), a handful of Neovim plugins with 8 stars or fewer, and essentially nothing maintained for PyCharm or Zed.

In notebooks, CE's built-in **`%%manim` magic** remains the standard. It renders and embeds the video in Jupyter or Colab, but Colab needs a full apt/pip setup every session, and the Binder example still points at a v0.9.0 tag, a sign of light maintenance ([CE docs](https://docs.manim.community/en/stable/installation/jupyter.html)). Only two notebook tools link controls to a scene, and both are single-maintainer projects with 10 stars or fewer. **manim-widget** serialises CE scenes to JSON and plays them in the browser through the TypeScript manim-web port; its author says the JavaScript was AI-written and not reviewed ([README](https://github.com/rambip/manim-widget)). **manim-marimo** re-renders *ManimGL* scenes when a marimo slider changes ([README](https://github.com/peter-gy/manim-marimo)).

The interactive shells moved in the latest CE release. ManimGL's `-se` plus `checkpoint_paste()` loop is still the most mature live workflow, but `manimgl` on PyPI is still 1.7.2 from December 2024 ([PyPI](https://pypi.org/project/manimgl/)). **CE 0.22.0 (8 October 2026) reworked the CLI**: `-l/--live-preview` now opens the OpenGL window, replacing `--force_window`. `--write_to_movie`, `--save_as_gif` and `--flush_cache` are gone, and a unified `--format` arrived ([0.22.0 changelog](https://docs.manim.community/en/latest/changelog/0.22.0-changelog.html)). The installed 0.22.1 source shows that `interactive_embed()` runs only with the OpenGL renderer, a live window and no file output, and that it needs IPython. The `--enable_gui` DearPyGui panel needs `dearpygui`. Neither IPython nor dearpygui is in this project's venv, and the Cairo renderer refuses `-l` outright. CE 0.22.1 has **no `--watch` flag**, so re-render on save always comes from an outside tool. The OpenGL path's long-standing weakness shows in the same changelog, which fixed OpenGL code paths that had been silently skipped because a renderer comparison never matched ([0.22.0 changelog](https://docs.manim.community/en/latest/changelog/0.22.0-changelog.html)). Users have called the DearPyGui panel "currently not very easy to use" and reported crashes with it under manim-voiceover ([OpenGL guide mirror](https://website-dw6.pages.dev/manim/opengl_guide); [manim-voiceover #57](https://www.github.com/ManimCommunity/manim-voiceover/issues/57)).

For presentations the field has consolidated. **manim-slides** (994 stars, MIT, PyPI v5.7.0 in September 2026) supports both CE and ManimGL with auto-detection, and offers a Qt presenter, reveal.js HTML, PowerPoint export, an IPython magic and a Sphinx extension ([README](https://github.com/jeertmans/manim-slides); [PyPI](https://pypi.org/project/manim-slides/)). manim-presentation and manim_editor are dead ([GH API](https://github.com/galatolofederico/manim-presentation)). Nobody has confirmed that 5.7.0 handles CE 0.22's removed CLI flags. Because manim-slides wraps `manim render`, that has to be tested before relying on it.

## Real CE never runs in a browser, and AI GUIs converge on "approve the plan"

**No Pyodide or JupyterLite build of Manim CE exists.** Cairo and Pango have no pure-Python wheels, so every browser front-end over *real* CE renders on a server or on your own machine. The official try.manim.community is just a redirect to a Binder notebook ([try.manim.community](https://try.manim.community/)). Client-side rendering exists only in reimplementations. **Academa Studio** loads a Rust/wgpu engine into Pyodide and renders on the user's GPU, with a Monaco editor, live preview and an AI agent. Its engine (ManimGX, MIT, about 2.8k stars) aims at the CE API but differs in imports, `.animate` timing and LaTeX, which it replaces with Typst ([HN](https://hn.svelte.dev/item/49091703); [ManimGX CE guide](https://manimgx.academa.ai/user-guide/coming-from-manim-ce/)). Hacker News users reported failures on Safari and Windows-on-ARM, and the hosted Studio costs $20 or $100 a month for paid tiers ([pricing](https://studio.academa.ai/pricing)). **manim-web** (519 stars, MIT) is a TypeScript port with a one-way `py2ts` converter. It claims all 429 "feasible" CE 0.22.0 public symbols, but users reported flicker and broken 3D lighting ([GitHub](https://github.com/maloyan/manim-web); [HN](https://hn.svelte.dev/item/47155375)). The one local browser studio over real CE with a timeline, birol-dev's Manim Studio/Composer, has 0 stars and has already changed its stated positioning once ([llms.txt](https://manim-fullstack.pages.dev/llms.txt)).

AI products mostly stop at "prompt → code → video". The richer GUIs have converged on one idea: **show the plan and get approval before writing code**. AnimG uses Spec → Approve → Process stages with a code playground ([animg.app](https://animg.app/en)). ManimCat has an editable planning card and a stage-timing panel, but runs on ManimGX and is AGPL-3.0 ([GitHub](https://github.com/Wing900/ManimCat)). **Animo**, from the Generative Manim author, is a desktop app for Mac, Windows and Linux. It costs $29 once and reuses your existing ChatGPT or Claude CLI subscription, with a chat pane, live preview and exportable CE code ([animo.video](https://animo.video/); [generative-manim](https://github.com/marcelo-earth/generative-manim)). None of these tools documents a timeline, per-object visual tweaks or a "re-render scene 3 only" control. None knows a project's house style. Hosted ones send prompts to third-party LLMs, and their pages only link to privacy policies. Generative Manim's self-hostable API had command-injection and path-traversal reports in 2026 ([GitHub](https://github.com/marcelo-earth/generative-manim)).

## Imperative scenes make true GUI round-tripping nearly impossible

The community's demand was never mainly about a canvas. The canonical CE discussion asks for **Grant's interactive loop in CE**: live output, "breakpoint" partial-scene rendering and interactive 3D navigation ([Discussion #3954](https://github.com/ManimCommunity/manim/discussions/3954)). In that thread a CE maintainer said even `section` rendering "still processes the whole scene", and that the render-loop refactor needed for Grant-style previewing had been in progress "for ages" with slow progress ([Discussion #3954](https://github.com/ManimCommunity/manim/discussions/3954)). A 2022 roadmap called a Blender-style GUI "hard" ([Roadmap wiki](https://github.com/ManimCommunity/manim/wiki/Roadmap)). The releases since then have gone the other way. v0.21.0 (August 2026) brought a 2.2× faster Cairo renderer, content-hashed caching, parallel encoding and Typst math without TeX, but no interactivity or preview UI ([0.21.0 changelog](https://docs.manim.community/en/stable/changelog/0.21.0-changelog.html)). **No official GUI is planned**, and the project is betting on a faster batch pipeline. That choice helps CLI and agent workflows, not GUIs.

The obstacles follow from Manim's design, and the notes support five of them. First, **there is no persistent scene graph**: to show frame *t*, a tool must execute `construct()` up to *t*. Caching speeds up playback, not edits. Second, **time is implicit** in call order and `run_time=` arguments, so dragging a clip means rewriting code. Third, **round-tripping arbitrary Python is unsolved**. Loops, helpers, updaters and `always_redraw` cannot be edited back from a canvas. That explains why diegormirhan refuses to import code, why AniMathIO converts out of Manim for good, and why canvas previews in LzdqesjG, Manim-Motion and EasyManim are only approximations. Fourth, **live scrubbing needs a GPU renderer**, and CE's OpenGL path is the less complete one. This project's 3D work deliberately uses Cairo. Fifth, **`dt` updaters, randomness and narration timing** make "jump to *t*" depend on replaying from the start.

The tools that work keep code authoritative and let the GUI edit a narrow, well-defined slice of it. **Motion Canvas** lets you drag "time event" pills to retime `waitUntil('event')` calls without touching animation code ([Motion Canvas docs](https://motioncanvas.io/docs/time-events)). **Remotion Studio** writes visual edits back to source, but only for inline literals; values computed in variables stay uneditable ([Remotion visual editing](https://www.remotion.dev/docs/visual-editing)). **JAnim**, a Manim-derived engine (MIT, v5.0.3 in November 2026), has a timeline, a draggable playhead and a VS Code extension that highlights the code line for the playing animation. Its draw tools only produce coordinates you paste into code yourself ([JAnim GUI docs](https://janim.readthedocs.io/en/latest/tutorials/use_gui.html)). In the Manim world, lukaznj's `run_time=` dragging and Manimble's "all three edit the same Python" follow the same pattern. Polylog's switch to Motion Canvas shows the cost of not having this: Tomáš Sláma cited the editor's "instant preview" alongside Manim pain points such as equation diffing and complex property animations that were "essentially impossible without some crazy updater shenanigans" ([slama.dev](https://slama.dev/motion-canvas/1/)).

The opposing view deserves weight. Experienced CE helpers in the same discussion said render time doesn't bother them and that sections are enough ([Discussion #3954](https://github.com/ManimCommunity/manim/discussions/3954)). Code-first scenes are diffable, parametric, reusable through helpers and, now, **editable by LLMs**, and a GUI-first tool gives all of that up. The most active new "interface" to Manim in 2026 is a coding agent. 3b1b's own videos repo ships a `CLAUDE.md` ([CLAUDE.md](https://raw.githubusercontent.com/3b1b/videos/master/CLAUDE.md)), and Remotion now ships agent skills for its Studio controls ([skill listing](https://mcpservers.org/agent-skills/remotion-dev/codex-plugin/remotion-interactivity)). An agent removes the cost of turning intent into code without needing a scene graph. Its weak spot is spatial judgment, which is why working agent setups add a viewer and automated checks. Hand control still wins in three places: nudging positions, retiming to narration, and picking colours. Each of these is cheaper to do by hand than to describe.

## This project already has the right shape and should borrow only pieces

Measured against the evidence, the current setup is the agent-plus-viewer-plus-checks pattern that the field is converging on. In some respects it is ahead of the commercial AI GUIs. It has one Scene per beat, single-scene re-renders, a plan-approval step in `plans/<video>.md` (the same idea as AnimG's Spec → Approve), layout and audio checks, and frame contact sheets. `preview_server.py` already does what Sideview does, re-rendering on save and playing the newest video, and it is editor-independent and shown in the Claude app's browser pane. The app is not VS Code, so Sideview itself adds nothing here.

The useful work is to **borrow features into the existing server rather than adopt a GUI**. Cue and lukaznj's studio point to the most valuable additions. The first is a scene timeline that lists each `play`/`wait` and narration line with its source line and lets you click to seek. `TimedScene` already knows its absolute marks and `.srt` cues, so the data exists. The second is a stale-frame "OUTDATED" badge while a re-render runs. The third is frame comparison (wipe or overlay) between the last two renders. Next on the list come the two GUI features that keep code authoritative: **named time marks stored in a sidecar file** that `at("mark")` reads, so retiming to narration is a drag rather than an edit (Motion Canvas's model), and **a small panel that edits the constants at the top of a scene file**. Remotion's `visualControl` shows that a panel like this works well alongside an agent. An audio waveform on the timeline would cover narration sync, which no Manim CE tool offers today. All of this is inference from the notes, not a tested design. One environment caution applies: project rules forbid installing packages without asking, so trials of Cue (which wants its own venv on CE `main`) or of CE's OpenGL GUI (which needs IPython and dearpygui) should happen in a separate environment, not in `.venv`.

## Conclusion

The question "which Manim GUI?" is the wrong one, because Manim's architecture limits any GUI to two jobs: showing the result of re-running code, or editing a narrow, typed slice of that code (a `run_time`, a time mark, a constant). Tools that respect that limit gain users and credibility. Sideview is the only hit, Cue comes from the core team, and Manimble already lets Claude Code edit alongside the canvas. Tools that ignore it stall at a few dozen stars. The 2026 shift toward agents does not make GUIs obsolete. It narrows what they are for: the agent handles intent and structure, while the GUI handles what agents do badly, namely seeing, timing and fine nudges.

For this project, the next gain is a richer viewer, not a different tool. Adding a code-linked timeline, mark retiming and a constants panel to `preview_server.py` would give it most of what the best 2026 GUIs offer, without bundled runtimes, licence entanglement or loss of `manim_kit.py`. The one external event worth tracking is the next Manim CE release. It is the point where Manim Cue becomes usable on stable CE, and the point to re-check manim-slides and the 0.22 CLI changes.
